# PLAN — Cycle GC: Generate Commit Message (Source Control sparkle) + Lite Model in AI Settings

## §1 Intent

The user likes Kilo Code's "Generate Commit Message" button in the VS Code Source Control
title bar and wants the same capability built natively into UnicDB — no Kilo dependency:

1. A `$(sparkle)` button in the SCM title bar (`scm/title`, `navigation` group), enabled only
   when there are git changes, that reads the repo diff and injects a Conventional-Commits
   commit message into the SCM commit input box.
2. A new **"Lite Model"** section in the existing **UnicDB AI Settings** panel — a fourth
   model role `lite` the user fills in (model ID), alongside work / smart / autocomplete.
   The Generate Commit Message feature runs on this Lite Model.
3. **Bug fix folded in (user-confirmed)**: the global **Engine** dropdown (`settings.engine`,
   `"builtin" | "omp"`) exists in the data model but was never rendered by the settings
   webview — `readSettings()` omits it, so every Save posts a settings object without
   `engine` and the host validator rejects it with "Engine must be builtin or omp". The form
   must render + round-trip the Engine field again.
4. The Lite Model defaults to the **omp engine** (user: "default vẫn là omp engine nhé"),
   while the global default engine stays `builtin` for back-compat. So the Lite role carries
   its own per-model `engine` override.

Success definition: user opens Source Control with pending git changes, clicks the UnicDB
sparkle, and the commit input box is filled with a conventional-style message generated by
the configured Lite Model — after having configured only a model ID in AI Settings. All
existing AI behavior (work/smart/autocomplete, chat engines) keeps passing the full suite.

## §3 Approach

**Lite Model = fourth role in the existing taxonomy (chosen) vs separate `UnicDB.commitGen.*`
configuration (rejected).** The codebase already models multi-model backends as roles
(`work | smart | autocomplete`) over one OpenAI-compatible baseUrl + SecretStorage key, added
incrementally without breaking older configs (Cycle AIC precedent). A separate settings
namespace would fork the provider/secret plumbing for no benefit. The coordinator's
per-model-engine recommendation is adopted: `AiModelConfig.engine?: AiEngine` (optional —
`undefined` inherits the global engine; `lite` defaults to `"omp"`). This keeps `work` /
`smart` / `autocomplete` configs byte-compatible and satisfies "global default stays
`builtin`" without a second top-level field.

**Bug root cause (Engine dropdown)**: verified in `webview/aiSettingsFormMain.ts` —
`readSettings()` (line ~96) and the validator mirror never carry `settings.engine`, while
host-side `aiSettingsErrors` rejects any settings object without `engine`. Fix = render the
select, post the field, mirror-validate. The bundle test locks this as a regression test.

**Git access (vscode.git extension API — chosen) vs `git.diff` command (rejected).**
`vscode.commands.executeCommand('git.diff')` is undocumented/unstable; the Git extension API
(`getExtension('vscode.git').exports.getAPI(1)`) is the same surface GitLens/Kilo use and
exposes `repository.diff(cached?)`, `state.*Changes`, `HEAD.name` and — critically —
`repository.inputBox.value`, which is the verified injection point for the commit message
(no `scm/inputBox` command exists in the current API). Structural local interfaces
(`GitRepositoryLike`) keep the adapter unit-testable without the real extension host.
Diff policy: staged diff (`diff(true)`) when non-empty, else unstaged; truncate at 12 KB.

**Engine routing (reuse — mandated).** Commit-gen reads `models.lite.engine ?? "omp"`.
`"omp"` → `detectOmp()` + existing `resolveEngine({detection, config})` (pure policy reuse;
its `path` threads into the ACP session per the Windows `.cmd` finding) and a one-shot
`createOmpChatEngine({..., mcpServers: []})` session (no DB tools needed; the `mcpServers`
override added in AIX-06-r3 makes this trivial). `"builtin"` → the exact
`createProviderClient({...cfg}).complete(req)` seam the AI Settings Test button uses, with
`req.modelId = models.lite.modelId`. If the Lite engine is `omp` but omp is unusable, the
command errors with the `EngineChoice.hint` instead of silently switching engines.

**Pure-core split for testability.** All three new modules keep vscode at the edges:
`collectCommitDiff(repo)` takes an injected repo; `commitMessage.ts` imports nothing vscode;
`runGenerateCommitMessage(deps)` receives every port (store, git, engines, inputBox, toasts)
as an options object, mirroring `AiSettingsFormOptions`.

**Menu ordering caveat (honest unknown).** Builtin git contributes `git.commit` and
`git.refresh` to a bare `navigation` group with no `@order` (verified in the local VS Code
app bundle). VS Code's tie-break for unordered items is not locally verifiable; the frozen
contribution uses the vision-spec verbatim `group: "navigation"`. If the sparkle renders
right of Refresh in the Dev Host, the fix is the single-string nudge documented in
TASK-GC-004 Discussion — everything else about the menu is test-locked.

|------|------|----------|
